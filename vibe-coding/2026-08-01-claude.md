### What actually happens when you tap the toggle in Tab 3

`InfoScreen`'s button → `AppViewModel.toggleSelectedItemDone()` (line 397), which does three things in sequence:

1. `items.setItemDone(...)` — appends one log row. But `appendActionLog` reads *today's whole log file* into memory, appends, then rewrites the entire file with `writeAll` (`"wt"`, truncate). Read-modify-write for a one-line append.

Counting SAF round trips in `loadChecklists`: for C checklists with N nodes each it's roughly `2 + C·(2 + 3N)` IPC calls. For 20 checklists × 15 items that's ~940 round-trips. At typical SAF/DocumentsProvider latency of a few ms each, that's seconds — which matches what you're seeing.

Note the `3N`: `loadOneChecklist` calls `childrenOf(dir.docId)` **twice per node folder** — once in the `filter` at line 136-140 to test for a README, then again at line 150 to fetch it. About a third of the scan is pure duplication.

### Correcting the diagnosis

- **The plaintext structure does cost you**, but mostly through repetition (3× per toggle) and because replay is O(entire history) — every `log-YYYY-MM-DD.csv` since day one gets read and parsed on every toggle. That grows linearly with how long you've used the app.
- **The index is not involved at all.** `ChecklistEntity` stores only `title`/`content` for FTS search — there is no done-state in Room. The README's claim that the index "speeds up state lookups" isn't implemented. So you aren't waiting on an index refresh; `reconcile()` only runs on launch and workspace-add.
- **The real headline: marking an item done doesn't change a single checklist file, yet `loadCurrent()` re-reads all of them.** That entire ~940-call scan is wasted work for a toggle.
- Secondary UX point: `_busy` is set in the ViewModel but **no UI reads it** (grep confirms). So there's no spinner — Tab 2 silently shows stale data until the flow updates, which reads as sluggishness rather than loading.

### Options

**Quick wins — no design change, no risk to the log-as-source-of-truth model**

1. **Optimistic in-memory update.** On toggle, immediately patch `_loaded.done` and `_selectedItem` with the state you already know, and let the log append happen in the background. Perceived latency drops to ~zero and Tab 2 is already correct when you switch. This alone likely resolves your complaint.
2. **Split `loadCurrent()` in two.** It conflates "re-read structure from disk" with "re-derive done-state." A toggle needs neither, but at most the latter. Separate `reloadStructure()` from `refreshDoneStates()` and have toggles call only the cheap one.
3. **Kill the duplicate `childrenOf` per node folder.** Fetch each node dir's listing once. ~30% off every scan, including workspace open.
4. **Stop replaying twice per toggle.** `loadCurrent` and `refreshSelectedItem` each call `loadDoneStates()`; pass the map through instead.
5. **Derive item history from the replay pass.** `loadItemLog` re-reads all logs to filter one item; the replay already parsed those rows.
6. **Append instead of rewrite.** Use `openOutputStream(uri, "wa")` in `appendActionLog`, with the current read-modify-write as fallback (provider support for `"wa"` varies). Also reduces truncation risk if the write is interrupted.
7. **Precompute sort keys.** `Naming.nodeSortKey` is called three times per comparison inside `compareBy` — decorate-sort-undecorate instead.

**Structural — for scaling as the log history grows**

8. **Incremental replay with a mtime/size watermark.** Keep replay as the source of truth, but cache the derived map and only re-read log files whose `lastModified`/size changed. Only today's file ever changes, so replay becomes O(today) instead of O(all history). `ChildInfo` already captures `lastModified`, so the plumbing exists.
9. **Make the Room index actually cache done-state** (as the README already promises). Add a table keyed by `(workspace, checklistFolder, itemFolder)` plus a watermark of the last consumed log file/offset. Reads come from SQLite; replay only catches up on the delta. This also fixes external edits cleanly and keeps the log authoritative.
10. **Cache parsed checklists by `(docId, lastModified)`** so re-opening a checklist doesn't re-parse unchanged READMEs.
11. **Paint structure first, overlay done-state when ready** — two-stage emission so the list renders immediately on first open.

**Worth deciding explicitly**

12. **Wire up `busy`,** or deliberately drop it. If you take option 1, an optimistic update is better than a spinner; but the flag being dead code is a trap for future work.

Supporting details worth knowing:

- A new `ItemRepository.Stamp` lets the ViewModel mint one instant, show it immediately, and hand the *same* stamp to the write — so the timestamp on screen is exactly what lands in the log, with no read-back.
