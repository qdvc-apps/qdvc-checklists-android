Room 2.6.1 and KSP are already wired up, so nothing new is needed on that front.

But I'd split your proposal in two, because the read half and the write half have very different risk profiles. The read half is a clear win. The write half is where all the hazards concentrate, and it's mostly optional for getting the speed you want.

### First, a correction on the hardware angle

Flash wear comes from program/erase cycles — writes, not reads. All that directory traversal costs CPU, Binder IPC, and battery, but it isn't meaningfully wearing your storage. So the traversal is a latency and battery problem, not a longevity one.

If longevity is a real concern, the actual write-amplification offenders are already in the code and are much cheaper to fix:

- `appendActionLog` reads the entire daily CSV into memory and rewrites the whole file to add a single row. Opening with `"wa"` (append) instead of `"wt"` (truncate) turns an O(file) write into an O(row) one, every single mark.
- A rename rewrites **every** daily log file in the workspace, via read-all-then-write-all per file.

Worth noting your proposal doesn't reduce total writes at all — it may add a few, since you'd write Room *and* eventually the files. So I'd pitch this change on responsiveness, and fix the append path separately for wear.

### The read half: recommend it

Making Room the read model is essentially what options A, B, and F were groping toward, done properly instead of piecemeal. Concretely: tables for checklists, nodes, and done-state, built by the existing reconcile pass, refreshed incrementally via `lastModified` rather than re-read wholesale.

Two benefits beyond speed that I think are underrated:

- **The UI gets reactive for free.** Room can expose `Flow` queries that Compose observes directly. That deletes most of the manual `loadCurrent()` / `refreshDoneStates()` / generation-guard plumbing we just added — including the optimistic-update machinery, since Room updates would propagate on their own. It's a genuine simplification, not just a cache.
- **Rebuildability is preserved.** Keep Room reconstructible from disk and a corrupt or wiped database is never data loss, which is what the README already promises and what `fallbackToDestructiveMigration()` currently assumes.

Two honest caveats. Cold start still needs one full scan, so the first launch against a large workspace stays slow — it just happens once, and only if you render from Room while reconciling in the background rather than blocking first paint. And the FTS schema needs rework: today it's one row per checklist with a concatenated `content` blob and an FTS4 `contentEntity` linkage to `rowId` (there's already a comment warning not to touch that field). A per-node read model means redesigning that linkage, which is fiddlier than it looks.

### The write half: proceed carefully

**The workspace is shared with the desktop Studio.** This is the big one. Read-once-at-launch means edits Studio makes while the app is running are invisible — and worse, a queued write-behind op computed against a stale Room view can clobber Studio's newer edit. The log format's `client` column shows the design already anticipated multiple writers; write-behind makes that assumption load-bearing. At minimum you'd want reconcile on resume rather than only on launch, mtime-based external-change detection, and an explicit decision about what happens on conflict.

**Fire-and-forget flushing becomes data loss.** Today every write is wrapped in `runCatching` and failures are silently dropped. That's *correct* right now, because disk is authoritative and Room is disposable — a dropped index update costs nothing. Invert the authority and a dropped flush means the user's files permanently stop matching what the app shows them. You'd need a durable, sequenced `pending_ops` table that survives process death and is drained on launch. Note that a coroutine in `viewModelScope` dies with the ViewModel, so the flush can't live there; WorkManager isn't currently a dependency.

**`fallbackToDestructiveMigration()` turns into a footgun.** It's the right call for a disposable cache. If Room holds unflushed writes, any schema change silently destroys user data. That needs real migrations, or a mandatory flush-and-verify before the destructive path is allowed.

**Ordering matters more than it appears.** Structural operations are path-dependent — create, then rename, then reorder. Replayed out of order the on-disk tree is simply wrong. The outbox has to be strictly sequenced per workspace. Coalescing helps (rename A→B→C collapses to A→C) but mustn't reorder dependent ops.

**Renames are the sharp edge.** One rename op touches the entire log history, with no atomicity in `rewriteCsvRows` — a failure partway leaves logs half-renamed. That risk exists today, but it's currently attended by a user watching a screen; write-behind moves it into the background where it fails unwitnessed.

Also: you said CRUD, but **delete doesn't exist yet** — there's no delete path for checklists or nodes at all. If you add it, tombstones and delete-then-recreate ordering become another outbox concern, so it may be worth designing that in from the start rather than retrofitting.

### The central fork

Does Room become authoritative, or stay a projection?

I'd keep **the logs authoritative on disk and Room a projection plus an outbox**. That preserves interoperability with Studio, keeps the database rebuildable, and means every failure mode degrades to "slow" rather than "wrong". The alternative — Room canonical, files as export — is cleaner to implement and faster, but it makes your app the owner of data that another application also edits, and that's where silent divergence lives.

2. Build the Room read model (nodes + done-state, incremental via mtimes). UI reads from Room; disk stays authoritative; writes still go to disk first, then update Room.
3. Move the UI to reactive Room `Flow`s and delete the manual reload plumbing.
4. *Only then*, if you still want it: outbox, write-behind, real migrations, and a visible "unsynced changes" indicator.

The thing worth noticing is that **step 2 alone eliminates both the switching lag and the marking lag**, with none of the write-behind risk. The write half buys you responsiveness on writes that optimistic updates already deliver.
